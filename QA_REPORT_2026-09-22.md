# Madinaty Deals QA report

**Date:** 22 September 2026
**Environment:** Production (`https://madinatydeals.com`) and local source/test environment
**Method:** Read-only production checks, Firefox browser automation, source review, unit tests, build/lint/type checks, and safe unauthenticated API requests. No production records, accounts, emails, reports, uploads, or listings were created or deleted.

## Executive Summary

- **Critical:** 0
- **High:** 6
- **Medium:** 13
- **Low:** 3

The public browsing experience is visually coherent, the category-specific rental and service filters largely reflect the requested product rules, CORS is exact rather than wildcard, admin APIs are protected, and the Cognito authorization-code flow uses PKCE, state, nonce, verified-email checks, secure cookies, and server-side sessions.

The largest release risks are in the marketplace workflow rather than the homepage. User submissions stop at a private review record and cannot be approved into public inventory. Advertisers cannot edit or remove submissions. Reports show a success message without reaching the server. Several service fields shown in preview are discarded before storage. The production HTTP endpoint is also served without an HTTPS redirect, which can break the secure Cognito state cookie and weakens transport safety.

The requested first end-to-end journey—new registration, email verification, and login—is **BLOCKED at the real confirmation-email stage**. The Cognito entry point, redirect, sign-up form, and safe malformed-email/password validation were tested successfully. A dedicated test inbox and confirmed Cognito-to-SES delivery were not available, so I did not create a real account or generate an authentication email.

## Architecture and Route Map

- **Frontend:** React 19, TypeScript, Vite.
- **Backend:** Native Node.js HTTP server.
- **Database:** PostgreSQL through Prisma.
- **Authentication:** Amazon Cognito managed login using OIDC authorization-code flow with PKCE. The callback verifies state, nonce, issuer claims, and `email_verified`, then creates a local PostgreSQL user and an opaque hashed-token session cookie.
- **Cognito:** User pool `eu-north-1_CQwYUlilX`, app client `1dgogb17ntlh64d0rfc5m0ki97`, region `eu-north-1`.
- **Uploads:** Private local Docker volume; image files are decoded and re-encoded with Sharp. Verification PDFs receive basic signature/type validation.
- **Deployment:** Docker Compose on Ubuntu behind Nginx and Cloudflare; the application binds to `127.0.0.1:3000`.
- **Public navigation:** React state-based home, browse, services, businesses, offers, saved, search, and admin views. Listing details use an `?ad=` query parameter.
- **Main API routes:** health/readiness/config, Cognito start/callback/logout, session/logout, uploads, resident verification, submissions, admin users, admin resident-verification reviews, views, and comments.
- **Public inventory:** Bundled fixtures in `src/data.ts`, not database listings.

## Major User Journeys

1. Visitor opens the homepage, selects a category, searches or filters static public inventory, and opens details in a modal.
2. Visitor chooses account access and is redirected to Cognito managed login for email/password or Google authentication.
3. Cognito redirects to the server callback; the server creates/updates the local account and session.
4. Signed-in user can submit a listing or service into a private `Submission` record.
5. A resident can upload residency evidence; an admin/reviewer can approve or reject the residency request.
6. Admin can manage account role/status and view browser-session demo analytics.

There is currently no journey from an approved submission to a public listing, no listing-owner management journey, and no server-backed report-review journey.

## BUG-001: Submissions cannot become public listings or be managed by their owner

**Severity:** High

**Area:** Listings / Admin / Marketplace

**Environment:** Production and source

**Steps to reproduce:**

1. Sign in and submit a listing or service.
2. Observe that the API creates a `Submission` with review status.
3. Open the admin area and public browse inventory.
4. Look for approve/publish, edit, status, and delete controls.

**Expected result:**

An admin can approve or reject the submission, approval creates a public listing, and the owner can later edit, mark sold, or delete it.

**Actual result:**

The submission remains a private review record. Public inventory is imported from `src/data.ts`. There are no listing-review, publish, owner-edit, owner-status, or owner-delete routes.

**Evidence:**

- `server/submissions.js` only creates and lists a user's own submissions.
- The only admin review routes are resident-verification routes.
- `README.md` and `DEPLOYMENT.md` explicitly say publication remains to be built.

**Likely cause:**

The project has a submission intake model but no publication state machine connecting `Submission` to `Listing`.

**Suggested fix:**

Add reviewer endpoints and UI for listing/service submissions; create a transactional approval operation that publishes normalized data and attaches uploads; add owner-authorized read/edit/status/delete endpoints; keep audit logs and test User A/User B isolation.

## BUG-003: HTTP is served without redirecting to HTTPS, breaking OAuth state safety on HTTP

**Severity:** High

**Area:** Authentication / Transport Security / Deployment

**Environment:** Production

**Steps to reproduce:**

1. Open `http://madinatydeals.com/?lang=ar`.
2. Observe that the site is served over HTTP instead of redirecting.
3. Start Cognito authentication from HTTP.
4. Observe that the response attempts to set a `Secure` `__Host-madinaty_oauth` cookie.

**Expected result:**

All HTTP requests redirect permanently to HTTPS before application/authentication handling. HTTPS responses include HSTS after HTTPS is stable.

**Actual result:**

HTTP returns the application directly. Browsers cannot persist a Secure cookie from an insecure context, so the callback can return a state-invalid error. HTTPS responses do not include HSTS.

**Evidence:**

- Read-only production GET returned HTTP 200 over plain HTTP.
- Cognito start uses a Secure state cookie.
- Production headers contain CSP/XFO/nosniff but no `Strict-Transport-Security`.

**Likely cause:**

Cloudflare/Nginx does not enforce canonical HTTPS, and the application assumes HTTPS at `APP_ORIGIN`.

**Suggested fix:**

Create a Cloudflare redirect from `http://*madinatydeals.com/*` to the canonical HTTPS apex while preserving path/query. Redirect `www` to apex. After verifying all HTTPS behavior, add HSTS at Cloudflare or Nginx.

**Files likely involved:**

- Cloudflare Redirect Rules
- Nginx virtual host
- `DEPLOYMENT.md`

## BUG-004: All proxied visitors likely share the same 60-requests-per-minute API limit

**Severity:** High

**Area:** API / Availability / Rate Limiting

**Environment:** Production architecture and source

**Steps to reproduce:**

1. Run the app behind Nginx as configured.
2. Send API traffic from multiple external visitors.
3. Inspect the key used by the general request limiter.

**Expected result:**

Each visitor has a safe, validated client key, or the limit is sized and stored for aggregate traffic.

**Actual result:**

`server/app.js` keys the 60/minute limiter only by `request.socket.remoteAddress`. Behind the local Nginx proxy this is normally `127.0.0.1`, so all visitors share one bucket. Moderate normal traffic can return 429 across the website.

**Evidence:**

- `server/app.js` uses `request.socket.remoteAddress` and ignores forwarded client addresses.
- Production architecture proxies all traffic through Nginx to loopback.

**Likely cause:**

Trusted proxy handling was removed while the rate limiter retained per-socket behavior.

**Suggested fix:**

Use a narrowly trusted proxy configuration that accepts an overwritten Cloudflare/Nginx client address only from known peers, or move rate limiting to Cloudflare/Nginx. Keep sensitive endpoint limits in the database. Test multiple simulated client IPs behind the proxy.

**Files likely involved:**

- `server/app.js`
- `server/rate-limit.js`
- Nginx configuration
- `.env.example`
- `SECURITY.md`

## Security Findings

### Positive controls verified

- Cognito uses authorization code + PKCE, random state/nonce, short-lived HttpOnly state cookie, verified email, and fixed callback URL.
- Local sessions use opaque tokens whose hashes are stored in PostgreSQL; cookies are HttpOnly, Secure, SameSite=Lax.
- Admin operations are protected server-side, not only hidden in the UI; tests cover role enforcement and last-admin protections.
- Upload retrieval checks ownership or reviewer role.
- Mutations require exact Origin and CSRF token where appropriate.
- Production CORS returns the canonical origin, never wildcard; a malicious Origin received 403 on mutation.
- API failures return generic JSON without stack traces.
- Content is rendered through React rather than raw HTML, reducing stored-XSS exposure.
- Missing JavaScript source maps returned 404.
- `npm audit --omit=dev --audit-level=moderate` found no production dependency vulnerabilities.

### Security risks requiring action

1. Enforce HTTPS and then HSTS (BUG-003).
2. Correct the proxy-aware rate limiter to avoid site-wide availability failures (BUG-004).
3. Publish an accurate privacy notice and retention policy, particularly for identity documents (BUG-008).
4. Verification PDFs receive basic type/signature validation but no malware scan. They are private and opened only by reviewers, which limits exposure, but the documentation currently claims scanning-related safeguards that are not deployed.
