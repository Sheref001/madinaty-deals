# S3 listing photos: setup and rollout

The code supports an opt-in, private S3 photo path. It is **not live** merely because this code is pushed. Keep `PHOTO_STORAGE=local` until the AWS resources, credentials, backups, and an end-to-end test are in place. Do not delete the existing upload volume or database records: existing `photo/` records remain local, and verification evidence remains local regardless of this setting. Category covers are static frontend assets and are unaffected.

## AWS resources (Europe/Stockholm, `eu-north-1`)

1. Create an S3 Standard bucket with a globally unique name. Leave Block Public Access fully enabled, ACLs disabled, and default encryption enabled. Turn on versioning only if you have a deliberate noncurrent-version expiration rule; otherwise copies and deletes can leave billable historical versions.
2. Configure S3 CORS for `https://madinatydeals.com` with method `POST`, allowed headers `*`, and no wildcard origin. Add the exact staging/local origin separately only while testing. The browser uses presigned POST rather than PUT because a POST policy can enforce `content-length-range` (5 MiB photo plus multipart form overhead); a presigned PUT alone does not reliably cap the uploaded bytes.

   ```json
   [{"AllowedOrigins":["https://madinatydeals.com"],"AllowedMethods":["POST"],"AllowedHeaders":["*"],"MaxAgeSeconds":300}]
   ```
3. Build a Node.js Lambda bundle containing `server/photo-worker.js`, `sharp`, and `@aws-sdk/client-s3` for the Lambda runtime and its Linux architecture. Use an S3 ObjectCreated event filtered to the `raw/` prefix; never trigger the worker for `active/` or `closed/`. Set `S3_PHOTO_BUCKET` and `S3_PHOTO_REGION=eu-north-1`. Allow the worker `s3:GetObject` and `s3:DeleteObject` on `raw/*`, and `s3:PutObject` and `s3:GetObject` on `active/*` (`HeadObject` is authorized by `s3:GetObject`). Set a dead-letter destination and alarm for failed processing; invalid files otherwise remain until the raw lifecycle expiry. Keep this Lambda outside a VPC unless private networking is actually needed, to avoid NAT gateway charges.
4. Give the backend an IAM role/identity scoped to the bucket: `s3:PutObject` and `s3:DeleteObject` on `raw/*`; `s3:GetObject` on `active/*` and `closed/*`; `s3:PutObject` on `closed/*`; and `s3:DeleteObject` on `active/*` and `closed/*`. S3 copy needs source `GetObject` and destination `PutObject`; there is no separate `CopyObject` IAM action. Never put AWS keys in frontend code or Git. Use a role or protected server-side environment credentials.
5. Add bucket lifecycle expiration for `raw/` after a short interval (for example one day) and `closed/` after your chosen retention period. No rule should expire `active/` automatically. Configure AWS Budgets and CloudWatch alerts for unexpected S3 storage, Lambda errors, and requests.
6. Only after AWS smoke tests pass, set `PHOTO_STORAGE=s3`, `S3_PHOTO_BUCKET=<bucket-name>`, and `S3_PHOTO_REGION=eu-north-1` in the **server's private environment**, then deploy by the documented production procedure. Test one real JPEG upload, resulting WebP, public visibility, owner close/archive, private evidence, and deletion/cleanup. Do not treat a Git push as deployment.

## Access and current limitation

The bucket must remain private. The API checks listing publication, owner status, and moderation state **before** reading a photo. New `active/` objects are private even while a submission awaits review. CloudFront direct delivery is deliberately **not wired up yet**: a public or long-lived CDN URL would bypass immediate hide/suspend checks. Configure no public CloudFront path to `raw/`, `active/`, `closed/`, or verification evidence. A later CDN integration must preserve these authorization and revocation semantics, likely with short-lived signed access and a documented revocation tolerance.

S3 stores files but does not compress them; the Lambda worker uses `sharp` to strip metadata, rotate, resize to 2000 px, and write WebP quality 80. The photo completion API validates the worker's object metadata before marking it ready. The existing `/api/public-uploads/:id` API still serves bytes, so bandwidth through the application server remains until a secure CDN design is implemented. Photo processing is best-effort asynchronous; failed processing surfaces as an upload timeout, with the raw object retained for investigation until lifecycle expiry. Failed archive operations are logged and require an operator retry; listing visibility is disabled by the database action regardless.

If an owner close/sold/remove action logs an archive error, correct the AWS problem and run `npm run maintenance:archive-closed-photos` in the configured server environment; it retries up to 100 closed photos per invocation. Do not delete old local photos based only on their `photo/` key: inspect production submissions first and take backups. No migration or bulk deletion is included in this change.
